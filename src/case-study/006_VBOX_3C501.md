# VirtualBox 3C501: Unbounded DMA Length Against a Fixed Packet Buffer

## Summary

This bug is caused by trusting a guest-controlled DMA length in the 3C501 emulation. The device uses a fixed 2 KB packet buffer, but the DMA transfer handler forwards the full ISA DMA length directly to the host DMA helpers without clipping it to the remaining buffer space. As a result, one DMA operation can read or write far past the end of the packet buffer.

## Trigger Chain

1. The guest programs an ISA DMA channel with a large transfer count.
2. The 3C501 DMA handler receives that count as the transfer length.
3. The handler copies the full length into the local transfer size.
4. The DMA helper is invoked on `abPacketBuf + current_pos` with the unchecked size.
5. The helper performs the full transfer, overrunning the fixed packet buffer.

## Vulnerable Logic

```c
uint32_t cbToXfer = dma_len;

rc = PDMDevHlpDMAWriteMemory(pDevIns, nchan,
                             &pThis->abPacketBuf[cur_pos],
                             dma_pos, cbToXfer, &cbXferred);
```

The same pattern also affects the opposite DMA direction, turning the same bug into either an out-of-bounds write or an out-of-bounds read.

## Fixed Logic

```c
uint32_t cbToXfer = dma_len;
uint32_t cbRemain = ELNK_BUF_SIZE - cur_pos;

if (cbToXfer > cbRemain)
    cbToXfer = cbRemain;

if (cbToXfer == 0) {
    PDMDevHlpDMASetDREQ(pDevIns, pThis->uIsaDma, 0);
    return dma_pos;
}
```

## Analysis

This is a bounds-check failure on a guest-controlled length. The critical mistake is that the code reasons about the DMA request length but forgets that the destination buffer is much smaller and fixed-size. Once that mismatch exists, the DMA helper becomes a generic memory corruption primitive. The proper fix is boring and obvious: compute the remaining capacity first, clamp the transfer, and stop the request if nothing can be copied safely.
